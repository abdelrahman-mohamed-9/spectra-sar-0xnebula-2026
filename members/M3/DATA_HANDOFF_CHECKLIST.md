# Data handoff checklist — M3 (Impact & Decision Intelligence)

## Required before first **full real-world** end-to-end test

### Member 1 — SAR Data Engineering (M1)
- Exact area of interest (AOI) Polygon/MultiPolygon GeoJSON, EPSG:4326 longitude/latitude, with event region; M3 can instead prepare an AOI if the team agrees on precise study region.
- Pre-event and post-event **real Sentinel-1 product IDs** or manifest, acquisition UTC dates/times, orbit direction, relative orbit when available, polarization (VV/VH), processing level, incidence-angle information, CRS, pixel spacing/resolution, footprint and no-data mask.
- Preprocessed/co-registered georeferenced SAR imagery files (GeoTIFF preferred) or cloud-accessible links **for M2**. M3 usually does not require full imagery directly if M2 delivers validated output, but the provenance must be passed downstream.
- Quality controls: co-registration/masking, coverage, known limitations and data download references.

### Member 2 — AI & SAR Change Detection (M2) **MAIN BLOCKER**
- **Required file:** `change_footprint.geojson`, real event-derived GeoJSON FeatureCollection of georeferenced polygon/multipolygon *candidate change footprint*, EPSG:4326, intersecting study AOI. If M2 outputs a raster mask (`.tif`) instead, M2 needs to polygonize it for the current M3 runtime or agree a new raster interface; do not rename a TIFF as GeoJSON.
- Required provenance: pre/post Sentinel-1 scene IDs, timestamps, polarization, orbit, preprocessing and change-detection method/version, spatial resolution, thresholding, invalid/layover/shadow masks, uncertainty/confidence definition and QA/validation notes.
- Explicit distinction between generic radar change vs validated flood/fire boundary; event label (`unknown` unless supported) and independent evidence if making claims.
- Optional helpful: confidence raster, GeoTIFF mask, visual before/after, pixel-level probability, validation precision/recall/IoU where available. Current runtime only accepts *polygon* footprint and a scalar `sar_confidence` for its basic scoring interface; richer confidence requires a future schema change.

### Member 3 — Geospatial & Decision Intelligence (M3; this package)
- **Required:** real `study_aoi.geojson`, selected event region and approximate date/year.
- OSM features GeoJSON (`osm_features.geojson`), raw `osm_overpass_raw.json`, and `source_manifest.json`: generated by bundled T02 on internet-connected machine, or supplied with URLs/timestamp/hashes.
- WorldPop population GeoTIFF (`worldpop_population_<year>_<resolution>.tif`) covering AOI, with explicit people-per-pixel vs density units, acquisition URL, year, license and georeference. Generated by bundled T02 if provider available; verify units independently.
- T03 analyst QA report and documented sign-off of WARNINGS; no override without review.
- Study-specific calibration/evidence for T06 risk score thresholds; existing defaults are screening estimates, not verified disaster-risk predictions.

## Downstream team handoff (not blockers for current local M3 test)
- **Backend/API integration owner:** API routes and schemas, authentication, IDs for event/project/run, storage convention and sample payload handling. M3 supplies `T09/api_contract.md` and output JSON files.
- **Frontend/dashboard owner:** output display requirements, map GeoJSON layer rendering, warnings, citations/provenance, uncertainty and status badges.
- **Other team roles (if assigned):** contact only where the team architecture explicitly includes their interfaces; M4/M5/M6 names are not assumed here.

## Minimum batch to send next
1. M1: `study_aoi.geojson` + `scene_manifest.json` (or scene IDs and dates).
2. M2: `change_footprint.geojson` + `change_metadata.json` (processing/method/validation).
3. M3 itself: download OSM & WorldPop by running `live_test.py` on the AOI.

**Check:** exact file schema and geographic projection, same location/event/time, credible provenance, no synthetic examples presented as findings. Do not submit secrets/API tokens.
